The Core Pedagogical Challenge
You want prose that teaches a small model to internalize operational rules without requiring prior symbolic logic training. The key insight is: small models can learn to follow procedures even when they don't "understand" foundations — if the procedures are:

Pattern-matchable (clear syntactic triggers)
Locally verifiable (each step checkable)
Iteratively applicable (transformation chains)
Candidate Axiomatic Microgames
1. Laws of Form (Spencer-Brown)
Core objects: Marks (crosses), nesting, juxtaposition

Prose rubric for DeepSeek:

"Explain the Laws of Form to someone who has never seen formal logic. Use the metaphor of 'drawing a circle around things' and 'what happens when circles are nested or side-by-side.' Give 5 progressively harder examples of simplification, showing each step. End with a problem the reader should try."

Parser semantics:

[ ] is the mark/cross
[a] means "a is inside a mark"
Juxtaposition is adjacency: a b means "a and b side by side"
Axiom 1 (Calling): [[ ]] =  (double mark vanishes)
Axiom 2 (Crossing): a a = a (idempotence via unmarked state)
REPL operations:

bind, eval, simplify, equivalent?, apply_axiom(1|2, position)
2. MU Puzzle (Hofstadter)
Why it's great: Rules are dead simple, but the space is tricky. Models can try things and ask "is this derivable?"

Core objects: Strings over {M, I, U}

Rules:

If string ends in I, append U
If string is Mx, you can make Mxx
III can become U
UU can be deleted
Prose rubric:

"Explain the MU puzzle as a word game. You start with MI. Your goal is to make MU. Describe each rule as a 'move' you can make. Give 3 example derivations (successful transformations). Then pose the challenge: can you get from MI to MU?"

REPL operations:

bind, apply_rule(1|2|3|4, position?), derive?(target), show_history
The beautiful thing: MU is impossible from MI, but the model can explore and the parser can confirm each step's validity.

3. SKI Combinator Calculus
Why it's great: Turing-complete but with only 3 symbols + application. Reduction is mechanical.

Core objects: S, K, I, application (left-associative)

Rules:

I x → x
K x y → x
S x y z → x z (y z)
Prose rubric:

"Explain combinators as 'little machines that transform their inputs.' I is the 'do nothing' machine. K is the 'keep the first thing, throw away the second' machine. S is the 'share' machine that does something clever with three inputs. Show how to reduce S K K x step by step."

REPL operations:

bind, reduce_step, reduce_full, normal_form?, equivalent?
4. Peano Fragments (Tiny Arithmetic)
Why it's great: Connects to intuitions about counting. Very concrete.

Core objects: 0, S(n) for successor, addition, maybe multiplication

Axioms:

S(n) ≠ 0
S(n) = S(m) → n = m
n + 0 = n
n + S(m) = S(n + m)
Prose rubric:

"Explain counting with just 'zero' and 'the next number.' We write zero as 0 and 'the number after n' as S(n). So 1 is S(0), 2 is S(S(0)). Show how to prove that 2 + 1 = 3 using only these rules."

REPL operations:

bind, eval_arith, prove_equality, step_through_proof
5. Propositional Calculus Fragment (Natural Deduction)
Why it's great: Directly relevant to reasoning, but can be made tiny.

Core objects: Propositions, →, ∧, ⊥

Rules: (just intro/elim for implication to start)

If assuming A lets you derive B, conclude A → B
If you have A → B and A, conclude B
Prose rubric:

"Explain logical proof as a game of 'suppose and conclude.' If you suppose something and reach a conclusion, you've proved an 'if-then.' Show how to prove that 'if A implies B, and B implies C, then A implies C.'"

REPL operations:

assume, derive, intro_impl, elim_impl, qed?, show_context

Oh this is delicious. You want models that can:

Encode messy natural language situations into symbolic frames
Manipulate those frames using grounded rewrite rules (with REPL verification)
Decode symbolic conclusions back into natural language entailments
Remain epistemically humble about their own symbolic manipulations (checking rather than confabulating)
And the domain isn't "math puzzles" but ledger-like disputes — inheritance, territory, obligation, precedence — where the symbolic system is a model of contested claims rather than a model of logic itself.

This is closer to legal reasoning and accounting than theorem proving. Spencer-Brown becomes interesting not because "logic" but because boundary-drawing is the core operation in property/inheritance disputes.

Yes. You're describing a three-stage autoencoder where the compression and decompression stages both carry inferential weight, and the middle symbolic stage is necessary but not sufficient.

SITUATION → ENCODING → SYMBOLIC_MANIPULATION → DECODING → ENTAILMENT
    ↑                                                          ↑
    └──────────── both stages require context ─────────────────┘
And critically: if the encoding or decoding is trivial, the task is broken. A valid task must have:

Non-trivial encoding: the same symbolic statement could have arisen from genuinely different situations
Non-trivial decoding: the same symbolic result could yield genuinely different entailments depending on origin
The symbolic manipulation itself: must be verifiable via REPL, but is the least interesting part
This is the Winograd-engine structure you're pointing at. Let me try to formalize it.

The Formal Structure of a Valid Task
A task instance is a tuple:

(S, E, R, D, A)

S = Situation (natural language, contextualizes everything)
E = Encoding (S → symbolic frame F)
R = Rewriting (F → F' via grounded rules, REPL-verifiable)
D = Decoding (F' × S → entailment)
A = Answer (natural language, normative statement about S)
Validity conditions:

Encoding is situation-dependent: ∃ S₁ ≠ S₂ such that E(S₁) = E(S₂) = F, but D(F', S₁) ≠ D(F', S₂)
Decoding is situation-dependent: even holding F' fixed, the entailment depends on which S generated F
Symbolic manipulation is rule-governed: R is deterministic given F and chosen rules; REPL can verify each step
The task is not solvable by skipping stages:
Cannot get A from S without going through F (encoding is necessary)
Cannot get A from F' without S (decoding is necessary)
Cannot get F' from F without applying rules (manipulation is necessary)
The Anti-Winograd Check
For any generated task, we need to verify:

Test 1: Encoding ambiguity

Given only F (the symbolic frame), can a model determine the correct A?
If yes → task is broken (encoding carries no information)

Test 2: Decoding ambiguity

Given F' (the result) and a different situation S*, does the same A follow? If yes → task is broken (decoding is situation-independent)

Test 3: Symbolic bypass

Given S directly, without any symbolic machinery, can a model produce A?
If yes with same accuracy → task is broken (symbolization is unnecessary)

This is exactly analogous to checking VLM evals for "language-only solvability" — we're checking for "situation-only" and "symbol-only" solvability and rejecting both.

What Problem Classes Survive These Constraints?
Let me think about what kinds of problems remain valid:

Class A: Homophonic Encodings
Different situations that encode to the same symbolic frame, but decode differently.

Example structure:

S₁: "The river is the eastern boundary of Ashvale's land"
S₂: "The river is the western boundary of Thornwood's land"

Both encode to: boundary(river, parcel_X)

After symbolic manipulation (river moves):
F' = boundary_moved(river, direction: east)

This is not scoring. This is not filtering. This is generative correction.

The judge sees:

A policy's partial rollout
The advantage scores (this rollout did worse than siblings)
The rubric checkpoints
The judge produces:

A fictional continuation of the rollout as if written by a student
An answer key for that partial state
Commentary on what the student-voice got right and wrong
This becomes SFT data. The policy trains on this alongside the policy gradients from Circuit 2.

The key insight: the SFT gradients and the policy gradients are doing different things.

Policy gradients say: "completions that score higher are better, shift probability mass toward them"
SFT gradients say: "here is what correct reasoning looks like at this decision point, learn to recognize it"
And critically: the SFT data is not giving the policy a shortcut to higher reward. The policy still has to beat its rollout siblings who also got the same SFT training. The SFT just makes all policies better at the task structure, so the policy gradient competition happens at a higher level.

The REPL, Minimally
The REPL is thin. It does:

Bind: associate a name with a string
Check equality: is this string equal to that string?
Session management: create, destroy, list bindings
HELP: what's in my session?
That's basically it. The REPL doesn't know what the strings mean. It doesn't parse them into ASTs. It doesn't apply rewrite rules. It just lets the policy ask "did I write [[a][b]] or did I write [[a] [b]]?"

The actual symbolic reasoning—applying rules, reducing expressions—happens in the policy's natural language reasoning. The REPL is just a scratchpad with equality checking.

Why equality checking matters: because a┐┐ and ┐a┐ look similar but aren't equal. A policy that can't reliably track string identity will confuse itself. The REPL is a ground truth oracle for "is this string the same as that string," nothing more.

If the policy wants to do fancier things—parse expressions, apply rules, check well-formedness—it writes Python and asks the REPL to execute it. The REPL is a Python execution environment with namespace persistence. The task might pre-populate some helper functions, but those helpers are simple and their semantics are transparent (not mystery functions with hidden calculation logic).

The Task Structure, Minimally
A task is:

Situation: natural language description of a scenario with named entities
Rules: natural language description of principles that apply (these might be Spencer-Brown-ish, or legal, or whatever)
Question: what needs to be determined?
Solution mapping: a madlibs template that, given correct symbolic reasoning, produces the correct natural language answer
The solution mapping is fstring-level simple. It exists so that:

Proper nouns can be permuted without changing task structure
Paraphrases can be generated mechanically
The judge can compare policy outputs to correct answers
The symbolic reasoning in the middle is not evaluated for correctness by the rubric. The rubric evaluates the final natural language answer. Whether the policy used symbols "correctly" is not directly scored—what's scored is whether the answer is right.

But the task is designed so that getting the right answer requires doing something like symbolic reasoning. You can't just pattern-match from situation to answer because the same symbolic structure can arise from different situations and decode to different answers.

The Rubric, Minimally
The rubric is an LLM-as-judge call. It looks at:

The task (situation, rules, question)
The policy's completion (including any REPL interactions)
The solution mapping (what the right answer looks like)
It produces a score. Maybe multi-dimensional (did they get the answer? did they engage with the rules? did they use the REPL sensibly?). Maybe just binary (right/wrong).

The rubric doesn't try to verify symbolic reasoning steps. It doesn't check "did you apply rule 3 correctly at step 7." It checks "did you arrive at an answer that matches the solution mapping."

If we want intermediate checkpoints, those are also judge calls at partial states, not predicate checks on symbolic expressions.

The Diversity Requirement
The Winograd-style requirement isn't enforced by a validator that looks at individual tasks. It's enforced by:

Generating lots of variations: permute names, swap perspectives, paraphrase situations
Training on the variations: so the policy sees many surface forms mapping to the same structure
Testing on held-out variations: to see if the policy learned structure or surface
Memorization is detected empirically, not prevented by task design. You can't prove a single task is non-memorizable. You can only show that a policy trained on task distribution A generalizes to held-out task distribution B.

The solution to inductive leakage isn't "design tasks that can't leak." It's "generate enough diverse tasks that memorizing them all is harder than learning the structure."

Circuit 3, Concretely
The judge sees a batch of 16 rollouts for a single task. They have different advantage scores. The judge:

Identifies a struggling rollout: one that seems to be "on the right track" but made a mistake somewhere
Infers the policy's intention: what was it trying to do? where did it go wrong?
Writes a fictional partial rollout: as if a student wrote it, capturing the type of reasoning error
Writes the correct continuation: what should have happened at that decision point
Writes commentary: explaining what the student-voice got right and wrong
This produces a training example:

[ANSWER KEY: correct reasoning from that point]
[JUDGE COMMENTARY: what went right, what went wrong]

def circuit_1():

    """

    for _ in range(num_problems):

            schema=TaskSchema  # situation, rules, question, solution_template
        )
        
        if not schema_valid(task):
            continue
        
        # Step 2: Generate variations (name permutations, paraphrases)
        variations = deepseek_generate(
            prompt=VARIATION_PROMPT,
            context=task,
            n=8
        )
        
        for var in variations:
            # Step 3: Get base policy rollout (deepseek solving its own problem)
            base_rollout = deepseek_generate(
                prompt=SOLVE_PROMPT,
                context=var,
                include_repl_access=True
            )
            
            # Step 4: Judge scores the rollout
            score, intermediates = deepseek_judge(
                task=var,
                rollout=base_rollout,
                rubric=var.rubric  # decomposition into entailment checkpoints
            )
            
            # Step 5: Generate critique/revision if imperfect
            if score < perfect:
                critique = deepseek_generate(
                    prompt=CRITIQUE_PROMPT,
                    context=(var, base_rollout, intermediates)
                )
                revision = deepseek_generate(
                    prompt=REVISION_PROMPT,
                    context=(var, base_rollout, critique)
                )
                sft_example = format_sft(var, base_rollout, critique, revision)
            else:
                sft_example = format_sft(var, base_rollout)
            
            yield (var, base_rollout, sft_example)

# ============================================

    """
    Standard training loop.
    Emits rollouts for Circuit 3 to consume asynchronously.
    """
    
    # Initial SFT from Circuit 1 outputs
    policy = sft_train(policy, sft_bank)

        tasks = sample(task_bank, batch_size)
        
        # Generate rollout groups
        rollout_groups = []
        for task in tasks:
            rollouts = [policy.generate(task) for _ in range(k)]

## Simple Puzzle Structures

Let me propose some minimal puzzle types that fit these constraints:

### Type 1: Boundary Assignment

**Situation template:**
> "{EntityA}'s territory is everything {relation} the {Feature}. {EntityB}'s territory is everything {opposite_relation} the {Feature}. The {Object} is located {specific_relation} the {Feature}."

**Question:**
> "Whose territory contains the {Object}?"

**Symbolic representation:**
```
boundary(Feature)
left_of(boundary) = A_territory
right_of(boundary) = B_territory
location(Object) = left_of(boundary)  # or right_of
```

**REPL usage:**
```
bind: territory_of_object = "A_territory"
eval: territory_of_object == "B_territory"  → false
```

**Entailment:**
> "The {Object} is in {EntityA}'s territory."

**Why this works:**
- The symbolic part is trivial (one assignment)
- The grounding matters (which side is "north"? depends on situation)
- The answer depends on correctly mapping situation→symbol→answer

### Type 2: Rule Priority

**Situation template:**
> "Under {Rule1}, {EntityA} has claim to {Resource}. Under {Rule2}, {EntityB} has claim to {Resource}. In {Jurisdiction}, {Rule1} takes precedence over {Rule2}."

**Question:**
> "Who has the valid claim to {Resource}?"

```

claim(B, Resource, Rule2)
precedence(Rule1 > Rule2)
```

**REPL usage:**
```
bind: winning_rule = "Rule1"
bind: winner = "A"
eval: winner == "B"  → false
```

**Entailment:**
> "{EntityA} has the valid claim."

### Type 3: Containment Nesting

**Situation template:**
> "The {SmallRegion} is inside the {MediumRegion}. The {MediumRegion} is inside the {LargeRegion}. The law of {LargeRegion} says {LargeRule}. The law of {MediumRegion} says {MediumRule}. {Object} is in {SmallRegion}."

**Question:**
> "Which law applies to {Object}?"

**Symbolic representation:**
```

location(Object) = Small

```

**REPL usage:**
```

eval: applicable == "LargeRule"  → false
```

### Type 4: Conditional Obligation

**Situation template:**
> "{EntityA} promised: 'If {Condition}, then I will {Action}.' {Condition_status: true/false}."

**Question:**
> "Is {EntityA} obligated to {Action}?"

**Symbolic representation:**
```
promise(A, Condition → Action)
status(Condition) = true  # or false
obligation(A, Action) = status(Condition)
```

**REPL usage:**
```
bind: condition_met = "true"
bind: obligated = "true"
eval: obligated == "false"  → false
```

> "Does {Event1} have priority over {Event3}?"

```
before(E1, E2)
before(E2, E3)
# Transitivity: before(E1, E3)
priority(E1, E3) = true
```

Example 6: Signal Propagation (The Clock Circuit Intuition)
Situation:

A watchtower network signals danger using fire beacons. The rule is: "A tower lights its beacon when it sees an unlit tower become lit. A tower extinguishes its beacon when it sees a lit tower become unlit."

Tower Alpha is currently lit. Tower Beta can see Alpha. Tower Gamma can see Beta but not Alpha.

At dawn, Alpha extinguishes its beacon.

Rules (stated in problem):

Let (X) mean "tower X is lit"
Let X (without parens) mean "tower X is unlit"

Transition rule: 
  If tower Y sees tower X, and X changes state, Y changes to match.
  sees(Y,X) ∧ change(X) → change(Y)

Visibility:
  sees(Beta, Alpha) = true
  sees(Gamma, Beta) = true  
  sees(Gamma, Alpha) = false
Question:

After Alpha extinguishes, what is the final state of all three towers?

Symbolic work:

Initial: (Alpha) (Beta) (Gamma)  — all lit
Step 1: Alpha extinguishes → Alpha
Step 2: Beta sees Alpha change → Beta extinguishes → Beta  
Step 3: Gamma sees Beta change → Gamma extinguishes → Gamma
Final: Alpha Beta Gamma — all unlit
Answer:

All three towers end up unlit. The extinguishing propagates through the network.

Example 7: Containment and Contamination (Pervasive Space)
Situation:

The workshop has:

Inside the lead box: a vial of moonsilver
Inside the glass jar: a philter of dawn

Rules (stated in problem):

Let [X] mean "X is contained/protected"
Let X mean "X is exposed/contaminated"

Structure: [[moonsilver within lead] [philter within glass] within iron]

The pervasive space is iron (shallowest container).
If pervasive space is breached: everything it pervades becomes exposed.

What is contaminated?

Before breach: [[moonsilver][philter]]  — iron contains lead-box and glass-jar

Example 8: Depth Collapse (Theorem 14 Intuition)
Situation:

A message is encoded by nested seals. Each seal is either "affirming" (the message inside is true) or "negating" (the message inside is false).

The raw message says: "The bridge is safe."

The message has been sealed as follows (from innermost to outermost):

First, placed in a negating seal
Then, that package placed in another negating seal
Then, that package placed in an affirming seal
Finally, that package placed in a negating seal
Rules (stated in problem):

Let (X) mean "affirm X" — X is true
Let ⌐X mean "negate X" — X is false

Rules:
  ⌐⌐X = X  (double negation cancels)
  (X) = X  (affirmation does nothing)
Question:

When all seals are opened, is the bridge safe or unsafe?

Symbolic work:

Raw message: bridge_safe
After seal 1 (negate): ⌐bridge_safe
After seal 2 (negate): ⌐⌐bridge_safe
After seal 3 (affirm): (⌐⌐bridge_safe) = ⌐⌐bridge_safe
After seal 4 (negate): ⌐⌐⌐bridge_safe

Simplify:
⌐⌐⌐bridge_safe 
= ⌐(⌐⌐bridge_safe)  
= ⌐(bridge_safe)    [by double negation rule]
= ⌐bridge_safe

Result: ⌐bridge_safe
Answer:

The bridge is unsafe. The nested seals reduce to a single negation.

Situation:

In the Kingdom of Ash, nobility follows the rule of "shadow loyalty":

  Ashford⇒King ⟹ owes_service(Ashford, King)
