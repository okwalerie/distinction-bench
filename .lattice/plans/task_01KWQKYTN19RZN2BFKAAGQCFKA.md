# DB-2: Text dialect families: archetypes plus novel self-similar dialects

## What this task delivers

Five new text dialects, each expressed as an archetype under the two-layer
architecture from `.lattice/notes/rendering-architecture-2026-07-04.md`
("the architecture note"). Every dialect encodes containment only. Colour,
vocabulary and glyph choice are cosmetic. Structure is verified by parsing
the emitted text back into a tree and comparing it to the source form, not
by trusting the renderer.

The five dialects, with their family and archetype key:

1. RNA dot-bracket notation — family `biopolymer`, archetype `rna_dotbracket@1` (new)
2. Indentation or tree-outline notation — family `trees`, archetype `tree_indent@1` (new)
3. Word brackets (BEGIN/END style) — family `parens`, archetype `parens@1` (reused, no new archetype)
4. Plain-English containment prose — family `prose`, archetype `prose@1` (new)
5. Nested clause embedding — family `embedding`, archetype `clause_embedding@1` (new)

This picks up the direct instruction to choose 3 to 5 dialects, taking RNA
dot-bracket notation as the top-ranked novel candidate, indentation, word
brackets and plain-English prose as the named text-family candidates, and
adding nested clause embedding as the second novel self-similar structure,
justified below.

A worked example runs through all five dialects. The example form is
`(()())`. Parsing it gives one top-level mark, call it node `0`, containing
two leaf marks, `0.0` and `0.1`. Every example below renders that same
tree, so the five outputs can be compared side by side.

## Sequencing against DB-4

DB-4 is still `in_planning` with no code landed. None of `FormNode`,
`containment_relation`, `relation_hash`, `Primitive`, `BaseRender`,
`Archetype`, `Injector`, `ComposedRenderer`, `ARCHETYPE_REGISTRY`,
`INJECTOR_REGISTRY`, `DialectSpec`, `verify`, or `emit` exist in the

implementation under that scheme. This creates a hard sequencing split.

**Phase A — can start now, no DB-4 dependency.** Write each dialect as a
pair of plain functions: `render_X(form_string, rng) -> str` and
`parse_X(rendered) -> list` (the nested-list form the codebase already
uses, see `lofbench.core.string_to_form`). These functions only import
`lofbench.core`. Test them by asserting
`parse_X(render_X(s, rng)) == string_to_form(s)` for a battery of forms,
including forms generated by `generate_form_string` at the boundary
conditions in `DIFFICULTY_CONFIGS` (widths up to 9, depths up to 9). Also
assert determinism: same seed, same output. This phase produces real,
tested, mergeable code today, independent of DB-4's timeline.

**Phase B — blocked on DB-4 landing M1 and M2 of its migration plan**: M1
(the core abstractions — `FormNode`, `containment_relation`, `relation_hash`,
`Primitive`, `BaseRender`, the `Archetype`/`Injector` protocols, the three
registries) and M2 (registry widening to a `Callable` factory type, plus
`DialectSpec` with named-factory registration). Wrap each Phase A function
pair as an `Archetype`, register it, add its `DialectSpec` entries, add the
two new injectors word brackets and the family-specific injectors need, and
wire provenance. This phase cannot be completed, and DB-2's stated
acceptance criteria (reachable via `-T renderer=...`, provenance recorded,
registry-key-equals-name test passing) cannot be met, until DB-4 lands M2.

Recommendation: implement and merge Phase A now. Hold Phase B until DB-4
lands M2. Do not mark DB-2 `done` on Phase A alone — the task's own
acceptance criteria require the registry wiring.

A module path is not fixed yet, because DB-4 has not decided one either
(its own plan file is still empty scaffold). This plan proposes
`src/lofbench/dialects_text/<name>.py` for the Phase A functions, one file
per dialect, as a placeholder that keeps them out of the existing
`renderers/` package (which holds the five legacy `FormRenderer`
subclasses that stay untouched per the migration plan). Expect this
directory to be renamed or moved when DB-4 fixes the real archetype
package layout in Phase B.

## Grammar pinning requirement (before Phase A)

Per orchestrator disposition: the prose, clause_embedding and tree_indent
dialects each leave at least one grammar choice implicit in this plan's
prose description. Before any Phase A code is written, the implementer
must pin each of the following formally (in the archetype's docstring or a
short grammar spec comment, not left to be decided ad hoc while coding):

- Prose (`prose@1`) and clause embedding (`clause_embedding@1`): the exact
  sibling-joining rule for a mark with three or more children (this plan's
  prose only shows the two-child case), and the exact "two empty boxes"
  collapse boundary — precisely which sibling patterns collapse to a
  counted plural noun phrase ("two empty boxes") versus which render as an
  explicit list, and whether that boundary is itself seed-independent (it
  must be, since it is part of the base render, not the injector).
- Prose (`prose@1`) specifically: numeral handling for counts 0 through 9
  at minimum (per `DIFFICULTY_CONFIGS`'s `max_width` up to 9) — the exact
  numeral words and the grammatical number agreement rule ("one empty box"
  vs "two empty boxes").
- Tree indent (`tree_indent@1`): comment-line syntax — the exact marker
  that makes a line a comment the off-side-rule reader must skip (for
  example a leading `#`), and its interaction with indent-jitter so a
  jittered comment line can never be mistaken for a sibling or child frame.

An unpinned grammar choice here is not a stylistic detail — it is a
determinism break. If the grammar itself makes an implicit choice at
render time (rather than the choice being fixed in the pinned spec, with
only vocabulary or whitespace left to the injector), two runs at the same
seed can diverge, or the round-trip parser can accept ambiguous input for
which two different trees would render identically. Fails review if any
of the three grammars above ships without its choices pinned in writing.

## The five dialects in detail

### 1. RNA dot-bracket notation

Family `biopolymer`. Archetype `rna_dotbracket@1`, modality text. New
archetype file.

RNA secondary structure is conventionally written as two aligned lines:
a nucleotide sequence and a dot-bracket structure line, one character per
base, matched parentheses marking a base pair, dots marking an unpaired
base. This is the standard Vienna/Zuker notation from bioinformatics, so
it is not an invented dialect — it is a real, well-known text convention
that happens to encode nested containment exactly.

Rendering `(()())`:

```
sequence   G C A U C G
structure  ( ( ) ( ) )
```

The structure line by itself is the same bracket skeleton as canonical
parens. What makes this a distinct archetype, not just relabelled parens,
is that the archetype always emits both lines together, and the sequence
line is not decoration bolted on afterwards — it is part of the base
render every time, seeded from the item seed. A dialect that emitted only
the structure line would risk a byte-identical payload to
`parens.canonical` on some forms, which the architecture note's freeze-time
collision check exists to catch. Emitting both lines as a unit avoids that
by construction.

Decomposition into archetype plus injectors: the archetype builds the
two-line base render and its node map (one entry per mark, keyed to its
position in the structure line; the sequence line carries no node ids).
One injector, `unpaired_filler` (modality `{"text"}`, applicability
archetype `rna_dotbracket@1`), inserts `.` characters at sibling
boundaries in both lines, mimicking single-stranded linker regions between
real RNA stems. Inserted dots get `node_id = None` — they are decorative,
exactly the "distractor content" the architecture note calls out, and they
cannot affect the induced containment relation by construction.

Round-trip: strip the sequence line, strip `.` characters from the
structure line, run the same bracket-matching reader canonical parens
already needs, rebuild the tree, compare relation hashes.

Seed determinism: sequence letters and dot placement both draw from the
item seed's decorrelated substreams (base sequence from the archetype's
own draw, filler placement from the injector's substream per the seed
threading scheme in the architecture note).

Coordination note for DB-3: DB-3's worked example 4 in the architecture
note is `rna_arc`, a spatial archetype in the same `biopolymer` family.
This text archetype is that family's text sibling. Nothing in the schema
stops one family spanning two modalities — `Archetype.modality` is a
separate field from `Archetype.family` for exactly this reason — but the
two archetypes should agree on vocabulary (base letters, family name)
where it is cheap to do so. Worth a one-line sync between whoever
implements each, not a blocking dependency.

### 2. Indentation or tree-outline notation

Family `trees`. Archetype `tree_indent@1`, modality text. New archetype
file.

Rendering `(()())`: one line per mark, children indented one level deeper
than their parent, using an off-side rule (the same technique Python's
tokenizer uses for indentation-sensitive blocks: a strictly deeper indent
opens a child, an equal indent is a sibling, a shallower indent closes
frames until the columns match again). The label token on each line is
decorative; only the indent column carries structure.

```
mark
    mark
    mark
```

Injector: `indent_style_jitter` (modality `{"text"}`, applicability
archetype `tree_indent@1`) can change the bullet glyph or label word per
line, insert blank or comment lines between siblings, and vary the number
of spaces per level, as long as each child's indent stays strictly deeper
than its parent's. That constraint makes the jitter safe by construction
under the off-side-rule reader, not merely safe in practice — the reader
only compares indent columns, never a fixed width, so varying the width
per render (or even per line, if the jitter is that aggressive) cannot
break parse-back.

Round-trip: an indentation-stack reader. Push a frame on a deeper indent,
pop frames on a shallower one, ignore blank and comment lines. Recovers
the exact tree shape independent of the actual whitespace used.

Seed determinism: the skeleton itself needs no randomness (like the
existing `sexpr` and `nested_list` renderers, it is a pure function of
tree shape). Only the injector draws from the seed.

Coordination note for DB-3: family `trees` is also DB-3's spatial
node-and-ring archetype for the same conceptual family. Same point as
above — shared family, different modality, no registry collision because
archetypes are keyed by `name@version`, not by family. Flag it so nobody
is surprised when `family == "trees"` shows both a text and a spatial
archetype in the analysis layer; that is intended, not a bug.

### 3. Word brackets (BEGIN/END style)

Family `parens`. Reuses archetype `parens@1`. No new archetype file — this
is a new `DialectSpec` on the existing archetype, in the spirit of "a
family is a config, not a class" from the architecture note's rejected
alternatives.

Rendering `(()())` with `BEGIN` / `END` tokens:

```
BEGIN BEGIN END BEGIN END END
```

Decomposition: the existing `bracket_swap` injector (migration step 5 in
the architecture note) is defined for single-glyph pairs, which can be
concatenated with no separator. Word tokens cannot — `BEGINBEGINEND...` is
ambiguous without whitespace. This needs either an extension to
`bracket_swap` to support multi-character tokens and a mandatory
separator, or a sibling injector, `word_delimiter_swap` (modality
`{"text"}`, applicability archetype `parens@1`), that takes a
`pairs: list[tuple[str, str]]` of word tokens (`BEGIN`/`END`,
`OPEN`/`CLOSE`, `START`/`STOP`), a mandatory separator (default one
space), and both a matched mode (one pair per depth, mirroring
`bracket_swap`'s non-mismatched mode) and a mismatched mode. This plan
leans towards the sibling injector, to keep `bracket_swap` itself simple
and single-glyph, but leaves the final call to whoever implements Phase B
— flagged as an open question below.

Round-trip: tokenise on whitespace, match each token against the
configured open/close word set (the reader already has to know the active
bracket vocabulary to invert non-ASCII glyphs for the existing
`noisy_parens` dialect, so this is not a new category of requirement),
rebuild nesting from the token stream.

Seed determinism: matched-versus-mismatched and pair choice draw from the
injector's substream, exactly like `bracket_swap`.

### 4. Plain-English containment prose

Family `prose`. Archetype `prose@1`, modality text. New archetype file.

Rendering `(()())`: "a box holding two empty boxes."

Grammar: a leaf mark renders as "an empty NOUN"; a mark with children
renders as "a NOUN holding" followed by a counted list of the children's
renderings, collapsing to "two empty boxes" when the children are
identical leaves. The base sentence must be a pure function of tree shape
— no unseeded stylistic branching inside the archetype itself, only the
injector below may vary wording. This is stated explicitly because it is
easy to accidentally break the "deterministic under seed" acceptance
criterion by letting the grammar itself make silent choices.

Injector: `synonym_jitter` (modality `{"text"}`, applicability archetype
`prose@1`) swaps "box" for "container", "vessel" or "crate", and "holding"
for "containing" or "enclosing", from a small closed vocabulary the reader
also knows.

Round-trip: a small recursive-descent parser over the fixed grammar.
Needs numeral words for 0 through 9 at minimum, since `DIFFICULTY_CONFIGS`
runs `max_width` up to 9. Knows the closed noun/verb vocabulary, including
every `synonym_jitter` substitution, and rebuilds the tree from the
"NOUN holding LIST" / "empty NOUN" pattern.

Seed determinism: synonym choice only.

### 5. Nested clause embedding (the second novel dialect)

Family `embedding`. Archetype `clause_embedding@1`, modality text. New
archetype file.

Justification for picking this as the extra novel self-similar structure:
recursive relative-clause embedding — "the rat the cat the dog chased
chased squeaked" — is a genuinely naturally occurring self-similar
structure in human language, independently studied in psycholinguistics
for its own processing-difficulty ceiling around depth three (Chomsky and
Miller's classic centre-embedding result). It directly answers the task's
own suggestion of "L-systems or nested clause embedding", and it gives a
dialect whose adversarial property — plausible model degradation at
depth, mirroring a known human limit — is independently interesting, not
just a restyled bracket. It is also clearly distinct from the prose family
above: prose uses explicit counting language in a descriptive register;
clause embedding uses bare recursive relative clauses with no count words
at all, using verb transitivity as the structural signal instead.

Rendering `(()())`: "the fox that watches the rabbit that hides and the
mouse that hides."

Grammar: a leaf mark renders as "the NOUN that V_intrans", using an
intransitive verb to signal "no further embedding". A mark with children
renders as "the NOUN that V_trans" followed by its children's renderings
joined with "and", using a transitive verb to signal "an embedded clause
follows". Verb transitivity class is the structural signal; verb identity
within a class is free to vary. As with the prose family, the base clause
skeleton must be a pure function of tree shape, with only vocabulary
choice left to the injector.

Correctness flag on this grammar, per orchestrator disposition: as written
above, the grammar right-branches — each mark's children are rendered as a
flat "and"-joined list appended after the head clause, which does not
reproduce the depth-3 centre-embedding difficulty the justification above
cites (Chomsky and Miller's result is about clauses nested inside the
subject position before the main verb, as in "the rat the cat the dog
chased chased squeaked", not siblings joined afterward). Either fix the
grammar to genuine centre-embedding — nesting each child's relative clause
inside the subject noun phrase, before its own verb, so processing
difficulty actually compounds with depth the way the cited psycholinguistic
result requires — or drop the processing-difficulty claim from the
justification entirely and keep clause embedding only as a self-similar
recursive structure with no borrowed difficulty claim. This plan prefers
the former: genuine centre-embedding. The implementer must pin the exact
grammar (how width — a mark with more than one child — maps onto a
strictly linear centre-embedding structure, since classic centre-embedding
is a single embedding chain, not a branching tree) before writing the
round-trip parser, and record the chosen grammar in the archetype's
docstring, per the grammar-pinning requirement above.

Injector: `vocabulary_jitter` (modality `{"text"}`, applicability
archetype `clause_embedding@1`) swaps in different nouns and different
verbs within the same transitivity class, from a closed vocabulary.

Round-trip: a recursive-descent parser keyed on "that" (marks an embed
boundary) and "and" (marks a sibling boundary), using a verb-transitivity
lookup table (closed vocabulary) to decide whether a clause is a leaf or
has children. Rebuilds the tree from the token stream.

Seed determinism: noun and verb choice only.

| `vocabulary_jitter` | `{"text"}` | archetype `clause_embedding@1` | new |

Every injector here is archetype-specific, per the amendment in the design
decisions note: "generic injectors stay single implementations;
archetype-specific injectors live with their archetype." None of these
five is generic enough to apply outside its own archetype (unlike, say, a
hypothetical family-agnostic whitespace jitter), so none belongs in a
shared generic-injector module.

## A note that applies to all five archetypes

Every archetype must build a `node_map` where every node id from the
source form's `FormNode` tree appears exactly once (the architecture
note's admission check enforces this). For text, the natural `Primitive`
for a node is a `"token"` or `"span"` kind carrying its character-offset
range in the emitted string, which is also useful for the site's sandbox
to highlight a node later. Any injector that inserts or deletes characters
(`unpaired_filler`, `indent_style_jitter` inserting blank lines,
`word_delimiter_swap`'s separators) must recompute those offsets, not just
edit the string. This is the same requirement the architecture note's own
worked example 2 already has for `whitespace_jitter`, so it is not a new
burden DB-2 invents — it is a shared concern for every text injector in
the project, worth restating here because all five of DB-2's dialects
depend on it.

## Test plan

Phase A tests assert, per dialect, for a battery of forms — `()`, `()()`,
`(())`, `(()())`, plus a handful generated by `generate_form_string` at
each `DIFFICULTY_CONFIGS` tier including the width-9 and depth-9 extremes:

- `parse_X(render_X(s, rng)) == string_to_form(s)` (round-trip)
- same seed gives byte-identical output across two calls (determinism)
- a jittered call (different seed, or the same seed with a jitter flag
  on) still round-trips, so the injector's structural safety is checked
  even before Phase B's formal `verify()` exists

Phase B tests add the registry and provenance checks listed above, plus
the project-wide checks the architecture note requires before any dialect
is admitted: registry-key-equals-name, node-map-exactly-once, and (once
the frozen suite exists) the freeze-time payload-collision guard across
all ten `DialectSpec` entries this task adds.

Run `uv run ruff check .` and `uv run pytest` after each phase.

## Acceptance criteria

- Each of the five dialects round-trips: the emitted text parses back to
  a tree whose containment relation matches the source form's.
- Each dialect is deterministic under a fixed seed.
- Each dialect is reachable via `-T renderer=<dialect_id>` (Phase B only;
  Phase A has no `-T` surface since it is not wired into a renderer yet).
- `uv run ruff check .` and `uv run pytest` pass.
- No model API calls anywhere in this task. No evaluation spend.

## Risks and open questions

- The DB-2/DB-3 label conflict described above. Flagged via a Lattice
  comment on DB-2; not resolved by this plan.
- Whether `predicate()` is meaningfully required on a text `Archetype` at
  all. The architecture note says text verification folds the parse-back
  tree instead of using a geometric predicate ("for text, fold the
  parse-back tree instead"), which suggests `predicate()` is unused for
  modality text, yet the `Archetype` protocol declares it unconditionally.
  Needs a decision from whoever implements DB-4's core: a stub, a default
  no-op on a text base class, or a protocol change.
- Word brackets: new `word_delimiter_swap` injector versus extending
  `bracket_swap` to support word-length tokens. This plan leans towards a
  new sibling injector; final call belongs to Phase B implementation.
- Phase A's module path (`src/lofbench/dialects_text/`) is a placeholder.
  DB-4 has not fixed the real archetype package layout (its own plan file
  is still empty scaffold). Keep Phase A modules small and dependent only
  on `lofbench.core`, to minimise rework when they move.
- The prose and clause-embedding grammars must commit to one deterministic
  base sentence per tree shape, with all randomness pushed into the
  injector. This is a real implementation risk, not a formality — it is
  easy to let a natural-language generator make silent unseeded choices
  (word order, pluralisation edge cases) that would quietly break the
  "deterministic under seed" acceptance criterion.
